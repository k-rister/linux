Executive summary

The CPU-accelerator work investigates whether Linux can remain the single operating system and control plane while one or more CPUs are leased to a protected, non-scheduler-governed dataplane execution domain. The goal is not a hypervisor or a second kernel. Linux performs admission, lifecycle control, resource accounting, recovery, and observability; the selected CPUs execute a statically admitted workload with ordinary Linux scheduling and routine IPI paths excluded from the active interval.

Phase 10 is complete. The implementation now supports an experimental ABI 25 static multi-worker domain with transactional activation, per-worker telemetry, manager-death cleanup, worker-targeted escape, bounded SPSC queues, and a linear static pipeline. ABI 23 and ABI 24 remain frozen compatibility floors. The implementation was validated on Simon with a two-CPU gate, a four-CPU gate, an ABI 23/24 freeze gate, and a twelve-hour corrected-isolation soak running user-oslat and rt-tests oslat concurrently.

The most important caveat is that this is still a bounded prototype rather than a production isolation system. NMIs, SMIs, machine checks, firmware effects, and some platform events remain outside the software control plane. Device and DMA ownership have not started. The current result demonstrates the lifecycle, memory, recovery, and static SMP model; it does not yet demonstrate a NIC-backed dataplane or a formal hard latency bound.

Original design

The original v1.1 design was written to make a Linux-integrated accelerator practical without changing Linux into a microkernel or adding a second operating system. It starts from a simple rule: every CPU boots online under ordinary Linux control. A user-controlled, coarse-grained transition can then move selected CPUs into accelerator mode and later return them to Linux without rebooting. There is deliberately no scheduler-driven time sharing between Linux and accelerator execution.

Primary goals

  • Single booted Linux OS with an accelerator execution domain.
  • User-controlled coarse-grained CPU lease and return.
  • No ordinary Linux scheduler or routine IPI path on active accelerator CPUs.
  • Preallocated shared-memory communication with bounded queues.
  • Fail-stop recovery and manager-death cleanup without host reboot.
  • Static multi-CPU domains before dynamic scheduling or device ownership.
  • Architecture-independent control plane with x86-specific backends.

Explicit non-goals

  • No hypervisor, guest, or second kernel.
  • No general accelerator scheduler.
  • No automatic rapid mode switching or time slicing.
  • No unbounded service execution during the dataplane interval.
  • No hard latency claim before platform and firmware effects are qualified.
  • No networking or device ownership until CPU ownership is stable.
  • No demand-paged DMA or mutable active address space in the target model.

Current architecture

The current implementation is an experimental kernel module and userspace SDK. Linux remains responsible for admission, configuration, resource accounting, and recovery. The accelerator domain receives a fixed CPU set, explicit shared-memory regions, and a statically admitted user image. The manager never remotely enters another process’s address space; each user worker joins the domain from its own execution context.

Control plane

/dev/cpu_accel exposes a singleton administrative domain. Opening the device requires CAP_SYS_ADMIN. A descriptor may be passed with SCM_RIGHTS. The manager owns the control mapping and creates or attaches shared regions. For user workloads, each worker process is pinned to its selected CPU, maps its own region and telemetry object, and joins the domain from its own memory map. This prevents the kernel from moving or redirecting another process’s address space.

Existing command numbers, argument types, and encoded sizes are immutable. New capabilities use new commands and new argument objects rather than appending fields to frozen structures. ABI 25 does not grow struct cpu_accel_config, struct cpu_accel_shared, or any ABI 23/24 object.

Memory model

The design separates four mapping classes:

  • CONTROL: Linux-owned control and status pages, mapped read-only by the worker.
  • ACCEL_PRIVATE: code, stack, and private state; mapped only in the accelerator address space and prefaulted before activation.
  • SHARED_REGION: explicit shared-memory regions between manager and worker.
  • DMA: registered pages additionally mapped into an IOMMU domain; not yet implemented.

ABI 22 replaced the fixed workload-data mapping with explicit variable-size regions. Regions are created while the device is idle, attached before configuration, and remain immutable while active. Region epochs change on attach, detach, reset, and reuse so stale mappings can be rejected. Active topology—region count, size, permissions, and tokens—is immutable.

Static SMP execution

An ABI 25 domain contains one fixed worker per selected CPU. The CPU set is immutable while configured. Admission rejects repeated CPUs, CPU 0, offline CPUs, multiple NUMA nodes, incomplete SMT sibling sets, and any set that leaves no usable Linux housekeeping CPU. Domain activation is transactional: every worker is prepared, entered, and published only after all workers report active. If any step fails, every started worker is stopped or unwound, Linux ownership is restored for every selected CPU, and the domain publishes ERROR.

Bounded SPSC pipeline

ABI 25 adds a second region type for single-producer/single-consumer queues. A static linear pipeline uses worker i as producer for queue i and worker i+1 as consumer. Queue capacity is a uniform power of two from 1 through 1024 slots. Producers and consumers spin without overwriting a full slot or consuming an empty slot. Slot publication and consumption use release/acquire ordering, and the producer-done bit terminates the drain only after the queue is empty. Queue coordination uses shared-memory polling; it does not use routine accelerator IPIs.

Key mechanisms

1. Transactional domain lifecycle

Domain activation is all-or-nothing. The driver validates every CPU, prepares every worker, reserves workqueue and IRQ resources, enters every worker, and publishes RUNNING only after every worker reports active. Any failure before full activation stops or unwinds every started worker, restores Linux ownership for every selected CPU, and publishes ERROR. A partially active or mixed Linux/accelerator domain is not an observable success state.

2. Sealed user image admission

A user workload is admitted from the exact task and memory map that will execute it. The worker’s image, stack, control mapping, registered RSEQ area, attached regions, and exact VMA set are validated before entry. The image and stack are pinned for the active epoch, and the worker’s mm is write-locked while active. The path deliberately excludes ordinary libc services, threads, signals, syscalls, dynamic allocation, and page-fault-driven initialization during the active interval.

3. Recovery and escape

ABI 25 provides a worker-indexed escape command. On x86, the kernel can send a local-APIC NMI to the target CPU; the registered handler redirects only a prevalidated user-mode frame for the active image to a prevalidated escape entry and stack. The escape path performs the terminal USER_EXIT syscall. This is an experimental recovery mechanism for the prototype, not a general interrupt-safe user ABI. Manager death, worker fault, watchdog expiry, and forced stop are domain-wide and fail closed.

4. TLB and memory ownership

The x86 path tracks TLB generations and owner acknowledgements for eligible same-mm work. Remote TLB flushes that target the owned mm can be deferred and reconciled on owner exit. The active mm is write-locked, excluding ordinary VMA changes while the worker is active. Page-table releases and drains with immediate walker barriers remain synchronous. This is one of the largest deviations from the original simple “stop Linux work on this CPU” model: real TLB, reclaim, and page-table interactions required explicit kernel-side coordination.

5. Workqueue and IRQ quarantine

While the target is entering or in accelerator mode, the workqueue core reserves it against unbound-work selection and redirects eligible unbound work to another online CPU. Per-CPU work remains associated with its target and is deferred until Linux mode resumes. IRQ quarantine is an explicit admission step that reserves the target against new normal IRQ affinity assignments, snapshots active affinity, moves migratable IRQs, and waits for in-flight handlers. It fails closed if an IRQ cannot be moved safely.

6. Per-worker telemetry

ABI 25 reports per-worker state, timestamps, counters, histograms, and terminal records through a separate telemetry mapping. The legacy shared mapping remains authoritative for ABI 23/24 and summarizes the domain when ABI 25 is selected. Telemetry includes context switches, migration, escapes, architecture interrupt and IPI counters, TLB events, workqueue activity, and lateness distributions.

Validation and results

The implementation was validated incrementally, with each phase gated on runtime behavior rather than only static builds. The most significant hardware validation is the Phase 10 SMP gate and the twelve-hour corrected-isolation soak on Simon.

Phase 8 adversarial validation

Phase 8 added a stress-class matrix that correlated user-oslat latency with external kernel activity. It covered baseline, CPU load, memory pressure, synchronous work, call-function IPIs, irq_work, timerlat, device lifecycle operations, power-policy transitions, resctrl, perf, ftrace, TLB flushes, hotplug, stop-machine, user escape faults, user death, RCU callback routing, migration, net backlog, and timer migration. The purpose was not to prove a universal bound, but to identify ordinary kernel paths that could stop the owned CPU and to validate that owner-aware handling kept those paths bounded and recoverable.

Important: The twelve-hour soak and Phase 10 gate are strong empirical evidence for the implemented execution model, but they are not a proof of absence of every ordinary Linux path or a formal hard latency bound.

Deviations and scope changes

The implementation stayed close to the architectural intent but deviated from the initial plan in several deliberate ways. These deviations are important because they explain why the project took longer in some areas and why device ownership has not yet begun.

1. Phase numbering shifted

The original v1.0 plan placed SMP at Phase 9, device/DMA ownership at Phase 10, and DPDK integration at Phase 11. The current implementation instead completed Phase 9 as UAPI/SDK freeze and Phase 10 as SMP. Device and static-DMA ownership moved to Phase 11 and have not started. This reordering reflects the prerequisite nature of ABI stability and static multi-CPU behavior.

2. Phase 8 expanded into kernel-wide work

The original plan treated adversarial validation primarily as a test phase. In practice, the audit found that many ordinary kernel paths could wait synchronously for work on an owned CPU. The project therefore added owner-aware synchronous-wait handling across several subsystems, including workqueue cancellation, device teardown, power policy, memory pressure, resctrl, perf, TLB, hotplug, stop-machine, and net backlog. This was necessary to make the ownership model viable rather than merely observable.

3. Memory and TLB ownership became a major subsystem

The initial design expected a sealed address space and prefaulted mappings. Real kernel interactions with TLB shootdown, mmu_gather, page reclaim, and same-mm ownership required explicit completion and acknowledgement paths. The current model write-locks the active mm, tracks TLB generations, and defers only eligible data-page batches while keeping page-table releases synchronous.

4. ABI evolution was more extensive than planned

The control plane evolved from a fixed mapping and small ioctl set to ABI 22 shared regions, ABI 23 exception telemetry, ABI 24 negotiation and architecture extensions, and ABI 25 SMP. ABI 23 and ABI 24 are now frozen compatibility surfaces, while ABI 25 remains experimental. The extension policy deliberately avoids growing frozen objects.

5. Device and DMA ownership were deferred

Device ownership remains Phase 11 and has not started. The plan intentionally requires a stable CPU ownership model, bounded communication, recovery, and ABI compatibility before introducing VFIO/IOMMUFD, BAR/MMIO exposure, interrupt routing, DMA quiesce, and device fault injection.

6. The implementation remains a bounded prototype

The current system does not fully own the local APIC, does not provide an IOMMU domain, and does not eliminate NMIs, SMIs, machine checks, firmware activity, or hardware execution effects. It also does not provide a general user-program ABI. The x86 ring-3 path is a cooperative proof with strict admission and escape constraints.

7. A twelve-hour soak was added after the Phase 10 gate

The original Phase 10 gate was a bounded validation. A twelve-hour corrected-isolation soak was added after the gate to provide stronger confidence in the corrected CPU-isolation configuration and in concurrent user-oslat and rt-tests oslat behavior. This was an extension of the validation plan, not a change to the architecture.

Suggested sharing narrative

For a technical audience experienced in low-latency and real-time workloads, the strongest narrative is not “we built a faster scheduler.” It is:

  1. Problem: Linux scheduling, IPIs, workqueues, TLB maintenance, and device activity can introduce latency that is difficult to bound on a CPU that must service a deterministic dataplane.
  2. Approach: Keep Linux as the control plane, but lease a static set of CPUs to a protected accelerator domain with explicit admission, bounded shared memory, and fail-stop recovery.
  3. Key mechanism: Use a transactional domain lifecycle, sealed user image, workqueue and IRQ quarantine, TLB ownership tracking, and per-worker telemetry.
  4. Result: A four-CPU static SMP domain and bounded SPSC pipeline passed the Phase 10 gate, and a twelve-hour concurrent soak showed zero user-oslat samples above 1 µs with a 400 ns maximum.
  5. Limit: Device/DMA ownership, networking, and formal hard latency bounds remain future work.

What is worth highlighting

  • The single-OS design and explicit non-hypervisor boundary.
  • The static multi-CPU execution model and absence of a general scheduler.
  • The transactional lifecycle and fail-closed recovery semantics.
  • The ABI compatibility discipline around versions 23, 24, and 25.
  • The bounded SPSC pipeline and memory-ordering contract.
  • The empirical validation on real hardware, including the twelve-hour soak.

What can probably be omitted

  • Most individual commit-level implementation details.
  • Test harness plumbing and routine build-validation commands.
  • Host-specific tuned-profile tuning unless the audience asks about the test environment.
  • Every Phase 8 subsystem audit row; summarize the class categories and outcomes.
  • Exact per-bin histogram tables unless latency methodology is the focus.
